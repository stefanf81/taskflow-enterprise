# Auth, CSRF, authorization and rate limiting

Web (cookie JWT + CSRF) and mobile (bearer) authentication, deny-by-default authorization, session hygiene and the rate limiter.

_Detail moved out of [`AGENTS.md`](../../AGENTS.md); the text is unchanged._

  - Auth: Stateless JWT in an HttpOnly `access_token` cookie (RSA-2048 asymmetric, OAuth2 Resource Server). `auth.interceptor.ts` catches 401s; `auth.guard.ts` is a `canActivateFn` that gates the `/admin` and `/customer` dashboards. The principal's role is restored from the backend via `GET /api/v1/auth/me` (reads the cookie) into an **in-memory** signal (`AuthState`) — it is never trusted from `sessionStorage`/`localStorage`.
  - CSRF: Double-submit pattern. The backend sets a readable `XSRF-TOKEN` cookie (via `CookieCsrfTokenRepository.withHttpOnlyFalse()`). Angular's `withXsrfConfiguration({ cookieName: 'XSRF-TOKEN', headerName: 'X-XSRF-TOKEN' })` in `app.config.ts` reads that cookie and attaches the header automatically on state-changing requests. The JWT `access_token` cookie is HttpOnly and **never** read by JavaScript — do not confuse the two. CSRF is disabled on public guest endpoints (`POST /api/v1/appointments`, `PUT /api/v1/appointments/public/cancel/*`, `POST /api/v1/reviews/public/**`).
- **Web Auth**: Stateless JWT in an HttpOnly `access_token` cookie (Asymmetric RSA-2048 signing via OAuth2 Resource Server). Role/identity is restored via `GET /api/v1/auth/me` into an in-memory Signal (`AuthState`) and never stored in `sessionStorage`/`localStorage`. CSRF protection uses the double-submit `XSRF-TOKEN` cookie.
- **Mobile Auth**: Native clients use `POST /api/v1/auth/mobile/login` and store the returned bearer token in `expo-secure-store`. The shared `/api/v1/auth/me` endpoint confirms the token on startup. Bearer-only requests do not require browser CSRF tokens; requests carrying the web `access_token` cookie remain protected.
- **Default credentials**: `admin` / `admin-password` in dev/test only. `SPRING_SECURITY_PASSWORD` is the source of truth for the admin account: `SecurityConfig.initAdminUser` re-syncs the stored hash from it on every boot. Under the `prod` profile `AdminPasswordGuard` aborts startup when it is unset, `admin-password` or a `CHANGE_ME` placeholder (`app.security.require-strong-admin-password`, default on in prod). Disposable stacks that run `prod` with the dev password (Compose, `.github/actions/start-backend`) opt out with `APP_REQUIRE_STRONG_ADMIN_PASSWORD=false`; real deployments must not.
- **`/actuator/prometheus`**: open while `app.metrics.scrape-token` (`APP_METRICS_SCRAPE_TOKEN`) is unset, which then relies on the production NetworkPolicy to keep the port internal (the prod profile logs a WARN at startup). Once it is set, only `Authorization: Bearer <token>` is accepted (`MetricsScrapeAuthorization`, hashed constant-time comparison; not even an admin JWT; a Prometheus `authorization.credentials` / vmagent `bearer_token` sends it). The scrape token is no JWT, so `cookieBearerTokenResolver` skips this path. Only `GET` is covered; `HEAD` and every other actuator endpoint stay ADMIN-only. Set the token in the GitOps repository (backend secret and scrape config) together. Test: `PrometheusScrapeTokenIntegrationTest`.
- **Authorization is deny-by-default**: `SecurityConfig` ends with `anyRequest().denyAll()`, so a new endpoint, or an HTTP method no rule names, is refused until it gets an explicit rule. Spring MVC serves `HEAD` from every `@GetMapping`, so every `GET` rule has a `HEAD` twin (an admin-only `GET` rule without one leaked `Content-Length`/existence of admin data). Admin handlers additionally carry `@PreAuthorize("hasRole('ADMIN')")` (`@EnableMethodSecurity`) as a second layer — keep both when adding endpoints, and add the `HEAD` case to `SecurityAuthorizationIntegrationTest`.
- **Session cookie hygiene & logout**: `StaleAccessTokenCookieFilter` validates the `access_token` cookie with the real decoder before the CSRF/bearer filters; an invalid one is expired in the response and hidden from the chain, so a dead cookie (key rotation, expiry, revoked token) cannot turn login/logout/public pages into 401s. `POST /auth/logout` is `permitAll` and puts the presented token's `jti` on `TokenRevocationList` (`app.state.store=redis` in prod: `SET revoked:<jti> 1 PX <remaining lifetime>` shared by all replicas, checked with one `PTTL` behind a local positive cache; on a Redis error it falls back to the local map, never rejects every token, and writes pending revocations once Redis answers; revocations are announced on `taskflow:token-revoked` so other replicas close their admin SSE streams. `memory` — the default for dev/test/the CDS build — keeps it per JVM. The mobile app calls the endpoint on logout). Every revocation is also written to PostgreSQL (`revoked_tokens`, V39, `PersistentTokenRevocations`); `TokenRevocationRestorer` loads the unexpired rows back into the local map and Redis at startup and every minute and deletes expired ones, so a logout survives a replica restart during a Redis outage and a Redis restart (Compose Redis also runs `--appendonly yes --appendfsync everysec`; mirror it in production). Requests never read that table. **Account-wide revocation (#218):** every token carries the account's `app_users.token_version` (claim `tv`, missing = 0); `AccountTokenCheck` (a decoder validator) rejects a token whose version is not current, whose account no longer exists, or whose account role is not among its authorities (demoted), reading the account at most once per 10 s per JVM (`forget` drops the cached state; a database error falls back to the cached state or accepts, like the Redis denylist). `revokeAllTokens` raises the version, applies at once on this replica and publishes `AccountTokensRevokedEvent`, which closes that account's admin SSE streams; the admin password re-sync in `initAdminUser` calls it. Use it for any future demote, delete or "sign out everywhere". `LoginAttemptLimiter` throttles failed logins per username + client IP (Redis fixed window `login_failures:<sha256>` shared by replicas with `app.state.store=redis`, per-JVM `FixedWindowCounter` fallback with the same limits; default 10 per 300 s → 429 + `Retry-After`; `app.rate-limit.login-max-failures=0` disables it). It is a temporary throttle, not a lockout, but it does let someone delay a known account's owner by one window.
- **Rate limiter**: classifies the bucket from the container-decoded servlet path (not the raw request URI), and on a Redis error falls back to a per-JVM `FixedWindowCounter` with the same limits (Redis is skipped for 5 s) instead of failing open. The fallback is per JVM by design, so with N replicas the effective limit during a Redis outage is up to N × the configured limit.
- **Prod fail-fast config**: `application-prod.properties` has no fallback for `APP_TRUSTED_PROXY_REGEX` and `APP_CORS_ALLOWED_ORIGINS`; startup aborts if either is unset. Write the proxy regex with *single* backslashes in YAML/env files (`^172\.(1[6-9]|2[0-9]|3[01])\.\d{1,3}\.\d{1,3}$`) — a doubled `\\.` reaches the JVM literally and never matches, putting every client in one rate-limit bucket. Under `server.forward-headers-strategy=native` the start also fails when the value is empty, does not compile or contains a doubled backslash (`core.web.TrustedProxyConfig`), and a filter counts every request that still carries `X-Forwarded-For` from a peer the regex does not trust (`taskflow_proxy_untrusted_forwarded_total`, the first one logged at WARN): the runtime symptom of a regex that matches the wrong proxy address (#219). Behind an ingress, mount a `/etc/nginx/real-ip.conf` (see `frontend/nginx-real-ip.conf`) with that ingress's range only; for peers it trusts, nginx also forwards the ingress's `X-Forwarded-Proto` (otherwise `http`), so the ingress must overwrite that header.
- **Personal data is `no-store`**: a response with customer or staff contact data (admin `GET /appointments` and `/{id}`, `barbers/admin`, `customer/appointments`, like the bearer token from `auth/mobile/login`) sends `Cache-Control: no-store`. `no-cache` is not enough: browsers and the mobile app's native HTTP cache (OkHttp disk cache on Android, NSURLCache on iOS) still write it to disk, where it outlives logout (OWASP MASTG-TEST-0052). An authenticated endpoint without an explicit tier inherits Spring Security's default `no-cache, no-store, max-age=0, must-revalidate`; `HttpCacheHeadersIntegrationTest` asserts both (BENCHMARKS.md §44).
