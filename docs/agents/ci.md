# CI and GitHub Actions supply chain

Action pinning, Renovate-tracked tool versions, job conditions and cache/coverage cost rules.

_Detail moved out of [`AGENTS.md`](../../AGENTS.md); the text is unchanged._

- **GitHub Actions Supply Chain**: every action, GitHub-owned `actions/*` and `github/*` included, is pinned to a full commit SHA with a `# vX.Y.Z` version comment: a tag can be moved to other code (in March 2026, 76 of 77 `aquasecurity/trivy-action` tags were force-pushed to malicious commits). `renovate.json` pins any new action via a `pinDigests: true` github-actions rule, and Renovate keeps each digest current from the version comment. Pin every new `uses:` the same way — never add a bare tag; zizmor's `unpinned-uses` audit in the `workflow-lint` job fails on one, and its online `impostor-commit` audit on a SHA that exists only in a fork. zizmor (pinned image, `ZIZMOR_IMAGE`, tracked by its own regex manager like actionlint) reads `.github/zizmor.yml`; a justified single-line exception is an inline `# zizmor: ignore[<audit>]` YAML comment, which for a finding inside a `run: |` block goes on the `run:` line (a `#` inside the block is shell text). Container images and tools used by workflows are pinned to an exact version through an annotated env var, picked up by the `customManagers:githubActionsVersions` preset in `.github/renovate.json` (not by the built-in github-actions manager, which only sees `uses:` refs): the `# renovate: datasource=… depName=…` line must sit directly above a variable whose name ends in `_VERSION`, as `TRIVY_VERSION` does. Removing that preset silently stops tracking it. `RENOVATEBOT_VERSION` instead contains a version and immutable digest and is tracked in both workflows by a dedicated regex manager in `.github/renovate.json`. The `prepull-buildkit` action's `moby/buildkit` default (`vX.Y.Z@sha256:<index digest>`, never `buildx-stable-1`) is tracked the same way through its `# buildkit-image:` marker, and so are `TESTSSL_VERSION`, `NIKTO_VERSION` (external scan; rolling tags `3.2` and `latest`, so the digest is the version and their Renovate group is never automerged) and `K6_VERSION`. Such a variable must not carry a `# renovate:` comment: the preset would then read `tag@sha256:…` as the version. The Renovate image (`ghcr.io/renovatebot/renovate`, runs with `RENOVATE_TOKEN`) has its own non-automerged group, so even its patch updates need review. Two more non-automerged groups: a digest-only change of a pinned action (its tag was moved; Renovate ages that against the original release date, so the soak does not apply) and the actions that publish, sign or attest the release images, hand over the scan report, or run Renovate (`renovatebot/github-action`, `sigstore/cosign-installer`, `actions/attest`, `actions/upload-artifact`, `actions/download-artifact`, `docker/login-action`, `docker/build-push-action`, `docker/setup-buildx-action`) — add an action to that rule when it starts to run in such a job. Both rules must stay below the automerge rule and the `GitHub Actions` group: later `packageRules` override earlier ones. The Trivy tarball itself is verified against a SHA-256 pinned in `.github/actions/install-trivy/action.yml` (`TRIVY_PINNED_VERSION` + `TRIVY_LINUX_64BIT_SHA256` below the `# trivy-release:` marker), not against the release's own checksums file; a regex manager with the `github-release-attachments` datasource moves version and checksum together, the `Trivy` group puts that in the same pull request as the workflows' `TRIVY_VERSION`, and the action (and `workflow-policy.test.cjs`) refuse a version without a pinned checksum. Do not name such a variable `RENOVATE_*` in `renovate.yml`: the action forwards that prefix into the Renovate container as config.
- **CI job conditions**: a job that must still run when one of its `needs` was skipped starts its `if:` with `!cancelled()`, never `always()` — GitHub re-evaluates a running job's `if:` on cancellation and keeps an `always()` job running, so a superseded run's E2E/image build would finish and hold up the newer run (§61). `.github/scripts/workflow-policy.test.cjs` (run by `workflow-lint`) fails on any job-level `always()`. Step-level `always()` is kept for teardown; SARIF/cache/summary steps that only need to run after a failure use `!cancelled()`.
- **CI caches & coverage cost**: `pushdockerimage.yml` uses no cache at all (`cache-mode: none`, `gradle-cache: disabled`, no `node_modules`/Angular/`type=gha`/Trivy cache; a policy test checks it): a release build must not restore an entry another workflow saved. Read-only `setup-gradle` jobs (`package`, `dependency-submission`, CodeQL, DAST, the weekly dependency audit) set `GRADLE_BUILD_ACTION_CACHE_KEY_JOB: backend` so they restore the `backend` job's entry (keyed by their own job id they restored a frozen wrapper/empty build cache); CodeQL builds with `--no-build-cache` so `javac` still runs under its tracer. `backend-integration` keeps its own entry and writes it from `main` pushes only, so PRs that do not touch the backend get `testcontainersTest`/`spotbugsMain` from the build cache. In `react-native-ci.yml`, `android-e2e` likewise keeps its own entry (written on `main`) with the build cache on: restoring the `android` job's entry (Debug, JDK 17) gave its Release/JDK 21 build no task hits. The dependency audit keeps no entry of its own: `delete-old-caches.yml` drops caches idle for 3 days, so a weekly writer only ever saved entries nothing reused. Every `setup-node` sets `package-manager-cache: false` and none uses `cache: npm` (the same policy test checks it): with the root `packageManager` field, setup-node otherwise caches npm by default, and a job that never runs `npm ci` saved an empty `~/.npm` that every other caller then exact-hit and never replaced. `npm-ci` restores `~/.npm` only on a `node_modules` miss (callers set `cache-node-modules: "true"`; DAST shares the CI frontend jobs' key); the weekly Expo maintenance and dependency audit only restore the `main` snapshot `react-native-ci.yml` saves. Playwright installs only `chromium-headless-shell`. The Trivy Java DB cache is keyed by its `DownloadedAt` and saved only after a real download; the vulnerability DB is not cached (stale 6 h after its build). The `test` task's JaCoCo agent instruments only `com.example.*`/`db.migration.*` (instrumenting Spring/Hibernate/H2 doubled each cold context start); the other `Test` tasks run without it. `test` forks get a 1 GiB heap (each keeps ~8 cached Spring contexts).
- **`react-native-ci.yml` manual runs and mobile gating**: `workflow_dispatch` takes a `target` input (`all` / `native` / `e2e`); the native build gate skips on `e2e` and the Detox gate on `native`, so verifying one half no longer pays for the other (~5 min of macOS, ~2.5 min of Linux per run). `Mobile JavaScript` always runs on a dispatch: it is the cheapest signal and the required-context gates aggregate it. The push trigger's `paths:` and the `changes` job's `dorny/paths-filter` list must stay identical — they gate the same inputs for different events — and `.github/scripts/workflow-policy.test.cjs` compares them. Both E2E jobs end with `.github/scripts/mobile-e2e-summary.sh`, which lifts the slowest backend requests, the connection-leak count and (iOS) the runner's load/swap/backend-memory extremes into the job summary; the artifacts still hold the full logs. The nightly builds `fast` (one ABI/arch) — `full` is a deliberate `workflow_dispatch`-only scope. The `native-fingerprint` job is **observation only**: it reports whether Expo's native fingerprint (the hash the Detox app caches are keyed on) differs between a pull request's base and head, next to what the native build gate's path/branch rule decided. It gates nothing and is in no job's `needs`. The rule has two known gaps the comparison is meant to close: with one root lockfile every npm update matches the mobile filter, so a frontend-only update builds both apps, and a native dependency added on a branch other than `renovate/*` / `maintenance/expo-sdk` builds neither while both required contexts still report success. Replace the rule with the comparison only once a few pull requests show they agree; the fingerprint covers installed native packages and autolinking, so each commit needs its own `npm ci` (two per run).
- **A cached failed dependency lookup**: when Backend build, Backend Package and Dependency Submission all fail in configuration on a dependency that does exist ("Could not find …pom") while `backend-integration` resolves it, the shared `backend` Gradle entry has stored a lookup that failed once (2026-11-21: kotlin-bom 2.4.21 after a Plugin Portal hiccup, red from `67ad713` to `0f80fe2`). Push a commit to `main` whose message contains `[gradle-refresh]`: its `backend` job runs with `--refresh-dependencies` and saves a clean entry for that SHA; jobs of that same run may still fail (they started from the old entry), the next run is clean. A dispatch cannot fix it (dispatches are read-only, and GitHub cache entries are immutable: the push run already saved the entry for the dispatched SHA); deleting the `backend` caches under Actions → Caches also works.
- **CI critical path**: a full `main` run is ~3 minutes and `backend` (the unit suite, ~116s of its 2m38s) is the long pole; `docker-backend` has 11s of slack, every other job more, so speeding up anything but the unit suite does not shorten the run. Do not propose persisting Gradle's configuration cache (`cache-encryption-key`): it was tried and never restored (BENCHMARKS.md §53, §59, §67).
- **DAST must prove it scanned something**: ZAP exits 0 for a scan the application never saw, and `dast.yml` ran that way unnoticed (§69: the per-IP limiter answered 99% of the requests with 429, and `ZAP_AUTH_HEADER_SITE` held a URL where ZAP expects a host-name substring, so the token was never sent). Keep the two `APP_RATE_LIMIT_*` overrides, `ZAP_AUTH_HEADER_SITE: localhost`, and the `zap-report` action's `min-served` / `require-success` / `token` inputs: they fail the job when the backend's own request counters show a throttled or unauthenticated scan, also with `fail_on_findings: false`. A new `.zap/*-rules.tsv` entry needs its reason in a comment and the narrowest form that works (`OUTOFSCOPE` with a URL regex before `IGNORE`); rule 100000 stays ignored for 4xx, while 5xx responses are findings counted from the backend. The web scan is a guest scan on purpose: the SPA only restores a session from its own cookies.
- **Published images are signed before they are promoted**: in `pushdockerimage.yml` the `push` job builds and pushes (`packages: write`, no scanner); the `scan` job runs Trivy with `packages: read` only, writes the report in Trivy's `cosign-vuln` format and reports the digest it scanned; the `promote` job takes the digest from `push`, fails unless `scan` reported that same digest (also with `skip_scan`), checks that the report names it and lists no finding, signs it with cosign (keyless, with a signed `scan=passed`/`scan=skipped` annotation), attests build provenance and the scan report (`actions/attest`), reads them back, and only then runs `imagetools create`, so a final tag never points at an unsigned digest. Keep `id-token: write` / `attestations: write` on `promote` alone and keep build, scan and third-party actions out of it: any step in a job with that token can sign as this workflow. Keep Trivy out of `push`: the scanner must not hold the token that pushes and tags. Never let `promote` take the digest it signs from `scan`: a compromised scanner could then name another digest of the package (an older release, a staged image that failed its scan) with a clean report and have it signed, attested and tagged; admission would accept it, since it checks that the attestations name the deployed digest, not that this run built it. The cluster (production manifests repository) admits only images signed by `pushdockerimage.yml@refs/heads/main` with `scan=passed`, provenance and the scan attestation, so renaming the workflow or the predicate type needs a change there too. Every Trivy image gate (this `scan` job and `ci.yml`'s `docker-backend`/`docker-frontend`) fails on a HIGH or CRITICAL vulnerability that has a fix, or a HIGH/CRITICAL secret: each sets `severity: HIGH,CRITICAL` together with `limit-severities-for-sarif: true`, without which `trivy-action` drops `severity` for SARIF output and gates on every severity (`workflow-policy.test.cjs` requires both on the three gates). The scan report is written with the same severities. The certificate identity is the workflow path plus the dispatched ref, so verifiers pin `…/pushdockerimage.yml@refs/heads/main`, and `:latest` moves only for a run from `main` (`image_tag: latest` is rejected for that reason). Signing fails closed (retried, no bypass input; recover with "Re-run failed jobs", which reuses the scanned digest). `promote` picks its component's digest in bash, never with `a && x || y`, which falls through to the other component's digest when one is empty. `workflow-policy.test.cjs` checks the step order (scan report checked before signing), that the signed digest comes from `push` and is compared with `scan`'s before any other `promote` step, the permissions of `scan` and `promote`, the actions `promote` may use and the absence of caches. How to verify: [`docs/ci/overview.md`](../ci/overview.md#verifying-a-published-image).
- **The external scan's TLS gate has one parser and fails closed**: `nightly-external-server-scan.yml` runs testssl.sh with `--jsonfile-pretty`, which writes an object (`scanResult[]` → host → section arrays), not the flat array `--jsonfile` writes. The former inline Python iterated that object's keys, raised on the first string and swallowed the exception, so the summary and the HIGH/CRITICAL gate reported a clean TLS setup on every run. `scripts/testssl_gate.py` now reads both shapes for the summary and the gate and exits 2 when it has no verdict (report missing, unparseable or empty, `scanProblem` FATAL, "Scan interrupted", testssl.sh exit status ≥ 242, no TLS target because HTTPS was unreachable); `fail_on_tls_issues: false` only downgrades findings, never those errors. Accept a known finding by id in `TESTSSL_ACCEPTED_IDS` with a reason, not by switching the gate off. `scripts/test_testssl_gate.py` runs it against unedited testssl.sh 3.2.5 reports (`scripts/testdata/testssl/`); regenerate them the same way (a throwaway local TLS server) when the JSON format changes, never from a production scan.
- **Every external-scan verdict needs proof that the scanner ran**: the scanners in `nightly-external-server-scan.yml` exit 0 for a scan that saw nothing, so each gate checks the report, not the exit status. Nmap with `--host-timeout` exits 0 and writes a host with `timedout="true"` and no ports; with `-Pn` a wrong or unreachable `TARGET_IP` has no open port either. `Extract open ports` records such cases (also an unparseable or missing XML, and "none of `EXPECTED_PUBLIC_TCP_PORTS` is open") in `reports/nmap-problems.txt`, and the gate fails on any line in it. Nikto 2.5 writes a JSON array with one object per host and exits 0 when it cannot connect (its only item is then "Unable to connect to …"); `run_nikto` marks both an unexpected shape and that message as failed. The Nuclei count has no `|| echo 0` fallback: results `jq` cannot evaluate fail the gate. Do not reintroduce `except Exception: pass`, `2>/dev/null || echo 0` or "empty list means clean" in a gate or its summary.
- **`jdk-next.yml` is an early warning, not a gate**: weekly (and on dispatch) it runs `test` and `testcontainersTest` on the JDK 28 early-access build (`-PtestJavaVersion`, which swaps only the test JVM; classes still compile on the Java 27 toolchain, ADR-024), and trains and boots the AOT cache on the floating `eclipse-temurin:27-jre-resolute` tag ahead of Renovate's digest. It is not a required check, uses `cache-read-only: true` plus `--no-build-cache`, and runs with each JDK's default compact object headers (on from 27; ADR-020 decision 6). On 28+ the test JVM also gets `-Djdk.reflect.allowNonSerializableConstruction=true`, without which Spring cannot instantiate CGLIB proxies (ADR-020 decision 7, a Java 28 upgrade blocker). Keep it out of branch protection; a red run means "read before the next Java upgrade".
