# CI and GitHub Actions supply chain

Action pinning, Renovate-tracked tool versions, job conditions and cache/coverage cost rules.

_Detail moved out of [`AGENTS.md`](../../AGENTS.md); the text is unchanged._

- **GitHub Actions Supply Chain**: third-party actions are pinned to full commit SHAs with a `# vX.Y.Z` version comment; GitHub-owned `actions/*` and `github/*` stay on tag refs (CodeQL `actions/unpinned-tag` exempts them). `renovate.json` pins any new third-party action via a `pinDigests: true` github-actions rule (GitHub-owned excluded), and Renovate keeps each digest current from the version comment. Pin every new third-party `uses:` the same way — never add a bare tag. Container images and tools used by workflows are pinned to an exact version through an annotated env var, picked up by the `customManagers:githubActionsVersions` preset in `.github/renovate.json` (not by the built-in github-actions manager, which only sees `uses:` refs): the `# renovate: datasource=… depName=…` line must sit directly above a variable whose name ends in `_VERSION`, as `TRIVY_VERSION` does. Removing that preset silently stops tracking it. `RENOVATEBOT_VERSION` instead contains a version and immutable digest and is tracked in both workflows by a dedicated regex manager in `.github/renovate.json`. The `prepull-buildkit` action's `moby/buildkit` default (`vX.Y.Z@sha256:<index digest>`, never `buildx-stable-1`) is tracked the same way through its `# buildkit-image:` marker. The Renovate image (`ghcr.io/renovatebot/renovate`, runs with `RENOVATE_TOKEN`) has its own non-automerged group, so even its patch updates need review. Do not name such a variable `RENOVATE_*` in `renovate.yml`: the action forwards that prefix into the Renovate container as config.
- **CI job conditions**: a job that must still run when one of its `needs` was skipped starts its `if:` with `!cancelled()`, never `always()` — GitHub re-evaluates a running job's `if:` on cancellation and keeps an `always()` job running, so a superseded run's E2E/image build would finish and hold up the newer run (§61). `.github/scripts/workflow-policy.test.cjs` (run by `workflow-lint`) fails on any job-level `always()`. Step-level `always()` is kept for teardown; SARIF/cache/summary steps that only need to run after a failure use `!cancelled()`.
- **CI caches & coverage cost**: read-only `setup-gradle` jobs (`package`, `dependency-submission`, CodeQL, DAST, image publishing, the weekly dependency audit) set `GRADLE_BUILD_ACTION_CACHE_KEY_JOB: backend` so they restore the `backend` job's entry (keyed by their own job id they restored a frozen wrapper/empty build cache); CodeQL builds with `--no-build-cache` so `javac` still runs under its tracer. `backend-integration` keeps its own entry and writes it from `main` pushes only, so PRs that do not touch the backend get `testcontainersTest`/`spotbugsMain` from the build cache. In `react-native-ci.yml`, `android-e2e` likewise keeps its own entry (written on `main`) with the build cache on: restoring the `android` job's entry (Debug, JDK 17) gave its Release/JDK 21 build no task hits. The dependency audit keeps no entry of its own: `delete-old-caches.yml` drops caches idle for 3 days, so a weekly writer only ever saved entries nothing reused. Every `setup-node` sets `package-manager-cache: false` and none uses `cache: npm` (the same policy test checks it): with the root `packageManager` field, setup-node otherwise caches npm by default, and a job that never runs `npm ci` saved an empty `~/.npm` that every other caller then exact-hit and never replaced. `npm-ci` restores `~/.npm` only on a `node_modules` miss (callers set `cache-node-modules: "true"`; DAST and image publishing share the CI frontend jobs' key); the weekly Expo maintenance and dependency audit only restore the `main` snapshot `react-native-ci.yml` saves. Playwright installs only `chromium-headless-shell`. The Trivy Java DB cache is keyed by its `DownloadedAt` and saved only after a real download; the vulnerability DB is not cached (stale 6 h after its build). The `test` task's JaCoCo agent instruments only `com.example.*`/`db.migration.*` (instrumenting Spring/Hibernate/H2 doubled each cold context start); the other `Test` tasks run without it. `test` forks get a 1 GiB heap (each keeps ~8 cached Spring contexts).
- **`react-native-ci.yml` manual runs and mobile gating**: `workflow_dispatch` takes a `target` input (`all` / `native` / `e2e`); the native build gate skips on `e2e` and the Detox gate on `native`, so verifying one half no longer pays for the other (~5 min of macOS, ~2.5 min of Linux per run). `Mobile JavaScript` always runs on a dispatch: it is the cheapest signal and the required-context gates aggregate it. The push trigger's `paths:` and the `changes` job's `dorny/paths-filter` list must stay identical — they gate the same inputs for different events — and `.github/scripts/workflow-policy.test.cjs` compares them. Both E2E jobs end with `.github/scripts/mobile-e2e-summary.sh`, which lifts the slowest backend requests, the connection-leak count and (iOS) the runner's load/swap/backend-memory extremes into the job summary; the artifacts still hold the full logs. The nightly builds `fast` (one ABI/arch) — `full` is a deliberate `workflow_dispatch`-only scope.
- **CI critical path**: a full `main` run is ~3 minutes and `backend` (the unit suite, ~116s of its 2m38s) is the long pole; `docker-backend` has 11s of slack, every other job more, so speeding up anything but the unit suite does not shorten the run. Do not propose persisting Gradle's configuration cache (`cache-encryption-key`): it was tried and never restored (BENCHMARKS.md §53, §59, §67).
- **DAST must prove it scanned something**: ZAP exits 0 for a scan the application never saw, and `dast.yml` ran that way unnoticed (§69: the per-IP limiter answered 99% of the requests with 429, and `ZAP_AUTH_HEADER_SITE` held a URL where ZAP expects a host-name substring, so the token was never sent). Keep the two `APP_RATE_LIMIT_*` overrides, `ZAP_AUTH_HEADER_SITE: localhost`, and the `zap-report` action's `min-served` / `require-success` / `token` inputs: they fail the job when the backend's own request counters show a throttled or unauthenticated scan, also with `fail_on_findings: false`. A new `.zap/*-rules.tsv` entry needs its reason in a comment and the narrowest form that works (`OUTOFSCOPE` with a URL regex before `IGNORE`); rule 100000 stays ignored for 4xx, while 5xx responses are findings counted from the backend. The web scan is a guest scan on purpose: the SPA only restores a session from its own cookies.
