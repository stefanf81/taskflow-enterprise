# CI and GitHub Actions supply chain

Action pinning, Renovate-tracked tool versions, job conditions and cache/coverage cost rules.

_Detail moved out of [`AGENTS.md`](../../AGENTS.md); the text is unchanged._

- **GitHub Actions Supply Chain**: third-party actions are pinned to full commit SHAs with a `# vX.Y.Z` version comment; GitHub-owned `actions/*` and `github/*` stay on tag refs (CodeQL `actions/unpinned-tag` exempts them). `renovate.json` pins any new third-party action via a `pinDigests: true` github-actions rule (GitHub-owned excluded), and Renovate keeps each digest current from the version comment. Pin every new third-party `uses:` the same way — never add a bare tag. Container images and tools used by workflows are pinned to an exact version through an annotated env var, picked up by the `customManagers:githubActionsVersions` preset in `.github/renovate.json` (not by the built-in github-actions manager, which only sees `uses:` refs): the `# renovate: datasource=… depName=…` line must sit directly above a variable whose name ends in `_VERSION`, as `TRIVY_VERSION` does. Removing that preset silently stops tracking it. `RENOVATEBOT_VERSION` instead contains a version and immutable digest and is tracked in both workflows by a dedicated regex manager in `.github/renovate.json`. The Renovate image (`ghcr.io/renovatebot/renovate`, runs with `RENOVATE_TOKEN`) has its own non-automerged group, so even its patch updates need review. Do not name such a variable `RENOVATE_*` in `renovate.yml`: the action forwards that prefix into the Renovate container as config.
- **CI job conditions**: a job that must still run when one of its `needs` was skipped starts its `if:` with `!cancelled()`, never `always()` — GitHub re-evaluates a running job's `if:` on cancellation and keeps an `always()` job running, so a superseded run's E2E/image build would finish and hold up the newer run (§61).
- **CI caches & coverage cost**: read-only `setup-gradle` jobs (`package`, `dependency-submission`, CodeQL, DAST, image publishing) set `GRADLE_BUILD_ACTION_CACHE_KEY_JOB: backend` so they restore the `backend` job's entry (keyed by their own job id they restored a frozen wrapper/empty build cache); CodeQL builds with `--no-build-cache` so `javac` still runs under its tracer. `backend-integration` keeps its own entry and writes it from `main` pushes only, so PRs that do not touch the backend get `testcontainersTest`/`spotbugsMain` from the build cache. `npm-ci` restores `~/.npm` only on a `node_modules` miss (callers set `package-manager-cache: false`); Playwright installs only `chromium-headless-shell`. The Trivy Java DB cache is keyed by its `DownloadedAt` and saved only after a real download; the vulnerability DB is not cached (stale 6 h after its build). The `test` task's JaCoCo agent instruments only `com.example.*`/`db.migration.*` (instrumenting Spring/Hibernate/H2 doubled each cold context start); the other `Test` tasks run without it. `test` forks get a 1 GiB heap (each keeps ~8 cached Spring contexts).
