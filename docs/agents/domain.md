# Domain rules: booking, lifecycle, outbox, SSE, catalog

Business invariants the backend enforces. Change them only together with the tests that pin them.

_Detail moved out of [`AGENTS.md`](../../AGENTS.md); the text is unchanged._

- **No-Preference Assignment (ADR-014)**: `No Preference (First Available)` is input-only; `BusySlotsService.findFirstAvailableBarber()` (uncached) resolves it to a scheduled, non-time-off, free barber inside the booking transaction, and the concrete `barberName`/`barber` FK are persisted. Never store the sentinel — the partial index cannot protect a fictitious barber name. `V26__assign_sentinel_appointments.java` repairs legacy rows (assign first eligible barber, else `DENIED`). No barber available → 400.
- **Idempotency Replay Binding (ADR-015)**: an `Idempotency-Key` replay is honored only for the same customer email + date/time/service/barber (sentinel = wildcard); verified replay → 200 via `AppointmentCreationResult.replayed()`, mismatch → `IdempotencyConflictException` → 409 with no booking body, fresh booking → 201. Header capped at 100 chars. The pre-check, the `23505` catch path and the validation-rejection catch path (a same-key winner committed before the loser's busy-slot read) all verify ownership.
- **Booking rules (one rule set, `BusySlotsService.evaluate`)**: used by create, admin approve and No-Preference resolution. `bookingTime` must be one of `ALL_SLOTS` (hourly grid), inside the barber's schedule, `start + service duration <= closing`, and must not overlap any PENDING/APPROVED booking of that barber/date (existing bookings count with their own service duration; a legacy row without a service counts as 60 min). It must be strictly in the future in the **shop time zone** (`ClockConfig`, `app.shop.time-zone`, default UTC — inject the `Clock`, never call no-arg `now()`), at most `app.booking.max-advance-days` (90) ahead, and a customer email may hold at most `app.booking.max-active-per-email` (5, serialised per address within one JVM) active future bookings. Violations are 400. Clients judge "past" and "too far ahead" in the shop zone too: `GET /api/v1/appointments/public/shop` (public, `{ timeZone }`, from the `Clock`) feeds `ShopClock` (web) / `useShopTimeZone` (mobile), and `shopWallClock` turns the instant into a Date whose local components are the shop's (visitor clock until the zone is known). Time-off start dates are checked against the same `Clock` in `BarberController` (not `@FutureOrPresent`, which uses the JVM zone); a barber cannot be named like the No-Preference sentinel. An unknown barber or malformed date on busy-slots is 400, never cached; a date nobody can book (before today in shop time or beyond `max-advance-days`) answers every slot busy without the per-date queries or a cache entry (`AppointmentServiceImpl.busyOutsideBookingWindow`); a transient DB failure there is 503 + `Retry-After` and nothing is cached (the old catch-all that cached "all busy" for 2 min is gone). An appointment occupies `[booking_time, booking_end_time)`: `booking_end_time` (V35, NOT NULL, CHECK end >= start) is start + service duration snapshotted at booking (60 min without a service, clamped at 23:59:59) and is what overlap checks use. `evaluate` is a pure function over a preloaded `BarberDay` (time off, weekday schedule, active bookings); `loadBarberDays` fetches those with a constant number of set-based queries, so No-Preference resolution issues 4 statements whatever the number of barbers (lowest barber id first; `NoPreferenceQueryCountIntegrationTest`). On PostgreSQL the `appointments_no_overlap` exclusion constraint (`EXCLUDE USING gist (barber_name WITH =, tsrange(booking_date + booking_time, booking_date + booking_end_time) WITH &&) WHERE status IN ('PENDING','APPROVED')`, needs the `btree_gist` extension) closes the race between overlapping bookings with different start times; SQLSTATE 23P01 is handled like 23505 (400 slot collision on create after the idempotency replay check, 409 on approve and in `GlobalExceptionHandler`). H2 has no exclusion constraints, so there the in-transaction check is the only guard for different-start overlaps. Raw SQL inserts into `appointments` must supply `booking_end_time`.
- **Appointment lifecycle**: statuses `PENDING`, `APPROVED`, `DENIED`, `CANCELLED`. Cancel is a **soft cancel** (customer, guest and admin `DELETE`): the row is kept as `CANCELLED`, the slot is freed, the idempotency key stays (a late replay returns the cancelled row, it does not rebook), and `AppointmentCancelledEvent(…, CancelledBy)` writes a proper "has been cancelled" outbox email. Only PENDING/APPROVED can be cancelled (already cancelled → idempotent 204, DENIED → 400); guests/customers cannot cancel a booking that has started, admins can. Admin status changes: PENDING→APPROVED|DENIED, APPROVED→DENIED, DENIED→APPROVED (full re-check: assigned real barber, not past, schedule, time off, overlap); same status is a silent no-op; anything else, or anything on CANCELLED, is 409 (`InvalidStatusTransitionException`). `Appointment` has `@Version` (stale write → 409). Adding barber time off cancels the barber's active bookings in the range and emails the customers; `createBarber` creates default Mon–Sat schedule rows (`app.booking.default-shift-*`, `default-working-days`). `reviews.appointment_id` is `ON DELETE RESTRICT`. Revenue uses `Appointment.priceAtBooking` (snapshot), so editing a price does not rewrite history. Admin search matches name/email/phone (contains) or publicId (exact), also with the OVERDUE filter; an unknown status filter is 400. Stats `total` excludes CANCELLED.
- **Flyway layout & seeds**: `db/migration` is schema + reference data (services, barbers, schedules). The demo bookings/reviews (V2, V11) live in `db/seed`, loaded only by the dev/test default `spring.flyway.locations`. The `prod` profile uses `db/migration,db/seed,db/prod-cleanup` (only the default `*:future` is ignored, so Flyway's missing-migration check stays on); `prod-cleanup/V30` removes the seed rows on every production database. Never edit a released migration (checksums are applied); there is deliberately no V16 (see `db/migration/README.md`). Java migrations V27/V28/V32/V35/V36 are dialect-aware (PostgreSQL vs H2); V36 adds PostgreSQL-only `pg_trgm` GIN indexes for the admin `LIKE '%term%'` search (operator class qualified with the extension's schema; skipped with a WARN if the extension cannot be created). The PostgreSQL-only tests (`AppointmentOverlapConstraintPostgresTest`, `DataMigrationsPostgresTest`, `BookingTimePreparationScriptPostgresTest`) are tagged `testcontainers` and use `testsupport/PostgresTestServer`: a throw-away container in `testcontainersTest` (CI `backend-integration`), or the server named by `TASKFLOW_TEST_POSTGRES_URL` (remember `--no-build-cache`/`cleanTest` since the variable is not a Gradle input). The preparation-script test runs `psql` on the host.
- **Notification outbox**: rows are claimed (`FOR UPDATE SKIP LOCKED`) and sent only while still `PROCESSING` under the same `(claimed_by, claimed_at)`; the result is a conditional update, so a reclaimed row can never be overwritten by a stale sender. Stale-claim reclaim counts the abandoned attempt (FAILED at 10), failures back off `30 s × 2^(n-1)` capped at 1 h via `next_attempt_at`, reminders are enqueued `PENDING` and re-checked (APPROVED, tomorrow in shop time) under the lock, and `app.notification.retention-days` (30) purges old SENT rows. `app.schedulers.enabled` (default true; false in the Gradle `test` task) guards the `@Scheduled` jobs.
- **Admin SSE**: registration/removal run inside `compute`; at the per-admin limit the *oldest* stream is evicted (reload/reconnect works) instead of 429; broadcasts and heartbeats go through a bounded executor (dropped + logged when saturated); heartbeats close streams whose JWT has expired, and a logout (token revocation, on any replica with `app.state.store=redis`) closes that token's streams. Appointment events are per replica, and role removal is not observed.
- **Catalog**: service names are unique case-insensitively (409 on clash); `DELETE` retires (`active=false`) a service that has bookings and hard-deletes one that has none; the public list, `GET /{id}` and booking see only active services. Hibernate L2/query caches are explicitly off (`l2-*` regions exist only for the benchmark).
- **No customer data in logs/traces**: `NotificationSender` logs only the outbox id and a masked recipient; the `appointment.customer` span attribute was removed. The `fail*`/`invalid*` recipient failure hook is off unless `app.notification.simulate-failures=true`.
