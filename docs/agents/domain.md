# Domain rules: booking, lifecycle, outbox, SSE, catalog

Business invariants the backend enforces. Change them only together with the tests that pin them.

_Detail moved out of [`AGENTS.md`](../../AGENTS.md); the text is unchanged._

- **No-Preference Assignment (ADR-014)**: `No Preference (First Available)` is input-only; `BusySlotsService.findFirstAvailableBarber()` (uncached) resolves it to a scheduled, non-time-off, free barber inside the booking transaction, and the concrete `barberName`/`barber` FK are persisted. Never store the sentinel — the partial index cannot protect a fictitious barber name. `V26__assign_sentinel_appointments.java` repairs legacy rows (assign first eligible barber, else `DENIED`). No barber available → 400.
- **Idempotency Replay Binding (ADR-015, `AppointmentBookingService`)**: an `Idempotency-Key` replay is honored only for the same customer email + date/time/service/barber (sentinel = wildcard); verified replay → 200 via `AppointmentCreationResult.replayed()`, mismatch → `IdempotencyConflictException` → 409 with no booking body, fresh booking → 201. Header capped at 100 chars. The pre-check, the `23505` catch path and the validation-rejection catch path (a same-key winner committed before the loser's busy-slot read) all verify ownership.
- **Booking rules (one rule set, `BusySlotsService.evaluate`)**: used by create, admin approve and No-Preference resolution. `bookingTime` must be one of `ALL_SLOTS` (hourly grid), inside the barber's schedule, `start + service duration <= closing`, and must not overlap any PENDING/APPROVED booking of that barber/date (existing bookings count with their own service duration; a legacy row without a service counts as 60 min). It must be strictly in the future in the **shop time zone** (`ClockConfig`, `app.shop.time-zone`, default UTC — inject the `Clock`, never call no-arg `now()`), at most `app.booking.max-advance-days` (90) ahead, and a customer email may hold at most `app.booking.max-active-per-email` (5, serialised per address within one JVM) active future bookings. Violations are 400. Clients judge "past" and "too far ahead" in the shop zone too: `GET /api/v1/appointments/public/shop` (public, `{ timeZone }`, from the `Clock`) feeds `ShopClock` (web) / `useShopTimeZone` (mobile), and `shopWallClock` turns the instant into a Date whose local components are the shop's (visitor clock until the zone is known). Time-off start dates are checked against the same `Clock` in `BarberController` (not `@FutureOrPresent`, which uses the JVM zone); a barber cannot be named like the No-Preference sentinel. An unknown barber or malformed date on busy-slots is 400, never cached; a date nobody can book (before today in shop time or beyond `max-advance-days`) answers every slot busy without the per-date queries or a cache entry (`AppointmentBookingService.busyOutsideBookingWindow`); a transient DB failure there is 503 + `Retry-After` and nothing is cached (the old catch-all that cached "all busy" for 2 min is gone). An appointment occupies `[booking_time, booking_end_time)`: `booking_end_time` (V35, NOT NULL, CHECK end >= start) is start + service duration snapshotted at booking (60 min without a service, clamped at 23:59:59) and is what overlap checks use. `evaluate` is a pure function over a preloaded `BarberDay` (time off, weekday schedule, active bookings); `loadBarberDays` fetches those with a constant number of set-based queries, so No-Preference resolution issues 4 statements whatever the number of barbers (lowest barber id first; `NoPreferenceQueryCountIntegrationTest`). On PostgreSQL the `appointments_no_overlap` exclusion constraint (`EXCLUDE USING gist (barber_name WITH =, tsrange(booking_date + booking_time, booking_date + booking_end_time) WITH &&) WHERE status IN ('PENDING','APPROVED')`, needs the `btree_gist` extension) closes the race between overlapping bookings with different start times; SQLSTATE 23P01 is handled like 23505 (400 slot collision on create after the idempotency replay check, 409 on approve and in `GlobalExceptionHandler`). H2 has no exclusion constraints, so there the in-transaction check is the only guard for different-start overlaps. Raw SQL inserts into `appointments` must supply `booking_end_time`.
- **Appointment lifecycle** (`AppointmentLifecycleService`; listings in `AppointmentQueryService`): statuses `PENDING`, `APPROVED`, `DENIED`, `CANCELLED`. Cancel is a **soft cancel** (customer, guest and admin `DELETE`): the row is kept as `CANCELLED`, the slot is freed, the idempotency key stays (a late replay returns the cancelled row, it does not rebook), and `AppointmentCancelledEvent(…, CancelledBy)` writes a proper "has been cancelled" outbox email. Only PENDING/APPROVED can be cancelled (already cancelled → idempotent 204, DENIED → 400); guests/customers cannot cancel a booking that has started, admins can. Admin status changes: PENDING→APPROVED|DENIED, APPROVED→DENIED, DENIED→APPROVED (full re-check: assigned real barber, not past, schedule, time off, overlap); same status is a silent no-op; anything else, or anything on CANCELLED, is 409 (`InvalidStatusTransitionException`). `Appointment` has `@Version` (stale write → 409). Adding barber time off cancels the barber's active bookings in the range and emails the customers; `createBarber` creates default Mon–Sat schedule rows (`app.booking.default-shift-*`, `default-working-days`). `reviews.appointment_id` is `ON DELETE RESTRICT`. Revenue uses `Appointment.priceAtBooking` (snapshot), so editing a price does not rewrite history. Admin search matches name/email/phone (contains) or publicId (exact), also with the OVERDUE filter; an unknown status filter is 400. Stats `total` excludes CANCELLED.
- **Self-service and weekly hours (V41)**: guests and customers can **reschedule** (`PUT /appointments/public/reschedule/{publicId}` with the booking email, `PUT /customer/appointments/{publicId}/reschedule`): `AppointmentReschedulingService` moves the same row (same barber and service, stored length kept), re-checks window, schedule, time off and overlap under the barber's shared lock, resets the status to `PENDING` and `reminderSent`, writes an outbox email and invalidates the old and new day's availability. The pickers ask **what this booking can move to** (`POST /appointments/public/reschedule/{publicId}/availability` with `{email, bookingDate}`, `GET /customer/appointments/{publicId}/availability?bookingDate=`; `no-store`, uncached): `BusySlotsService.busySlotsForMove` applies the same rules with the booking's own barber and stored length and ignores the booking itself, so it may move within its own interval and a service renamed or retired since does not matter (the create-time `busy-slots` counts the booking and reads the length from the active catalog, so it refused both). Past slots and days outside the window are all busy; a wrong email, a cancelled booking and an unassigned barber answer like the move (404, 409, 409). `creation_request_fingerprint` (V41, backfilled; email, barber, date, time, service) freezes the original create request, so an `Idempotency-Key` replay still matches after a move. **Calendar export** (`POST /appointments/public/calendar/{publicId}` with the email, `GET /customer/appointments/{publicId}/calendar`) returns RFC 5545 text (UTC, the stored end time, no contact data) as `{content, filename}` with `no-store`; a wrong email and an unknown id answer the same 404. **Weekly hours** (`GET`, `POST …/preview`, `PUT /barbers/{id}/schedule`, admin): every change carries the schedule's `revision`; the preview counts the future bookings outside the new hours and returns their `conflictsRevision`, and a save that would cancel any needs `cancelConflictingAppointments=true` with that revision (409 otherwise, or when either changed meanwhile). Schedule and time-off writes take the barber's `PESSIMISTIC_WRITE` lock, bookings and approvals a `PESSIMISTIC_READ` one (`findByIdForBooking`, `findAllForBooking` for No Preference), so a change cannot interleave with a booking's checks.
- **Flyway layout & seeds**: `db/migration` is schema + reference data (services, barbers, schedules). The demo bookings/reviews (V2, V11) live in `db/seed`, loaded only by the dev/test default `spring.flyway.locations`. The `prod` profile uses `db/migration,db/seed,db/prod-cleanup` (only the default `*:future` is ignored, so Flyway's missing-migration check stays on); `prod-cleanup/V30` removes the seed rows on every production database. Never edit a released migration (checksums are applied); there is deliberately no V16 (see `db/migration/README.md`). Java migrations V27/V28/V32/V35/V36 are dialect-aware (PostgreSQL vs H2); V36 adds PostgreSQL-only `pg_trgm` GIN indexes for the admin `LIKE '%term%'` search (operator class qualified with the extension's schema; skipped with a WARN if the extension cannot be created). The PostgreSQL-only tests (`AppointmentOverlapConstraintPostgresTest`, `DataMigrationsPostgresTest`, `BookingTimePreparationScriptPostgresTest`) are tagged `testcontainers` and use `testsupport/PostgresTestServer`: a throw-away container in `testcontainersTest` (CI `backend-integration`), or the server named by `TASKFLOW_TEST_POSTGRES_URL` (remember `--no-build-cache`/`cleanTest` since the variable is not a Gradle input). The preparation-script test runs `psql` on the host.
- **Review ratings (V38, ADR-022 Follow-up 3)**: a review carries its appointment's `barber_name` and `counted` (appointment still APPROVED). `ReviewRatingInputsListener` updates `counted` from the status/cancel events inside the status transaction (like the outbox writer) and evicts the cached `barberRatings` after commit only when a counted review changed; the aggregate is one `GROUP BY` over `reviews`. Never compute ratings by reading the appointment table from `review`, and a migration that rewrites the status or barber of reviewed appointments must update both columns. A "No Preference" booking skips the second `findConflict`: the resolution already applied the same rules in the same transaction.
- **Notification outbox**: one relay run claims batches of at most 50 until a batch comes back short or 20 s pass (`NotificationRelayScheduler.DRAIN_BUDGET`), checking the budget before every batch/send and releasing unstarted claims without charging an attempt. Claim validation/snapshot and conditional outcome writes use short transactions; SMTP runs outside any database transaction. Only the same `(claimed_by, claimed_at)` may write an outcome, so a reclaimed row can never be overwritten by a stale sender; SMTP acceptance followed by a crash remains at-least-once. Stale-claim reclaim counts the abandoned attempt (FAILED at 10), failures back off `30 s × 2^(n-1)` capped at 1 h via `next_attempt_at`, reminders are enqueued `PENDING` and re-checked (APPROVED, tomorrow in shop time) under the lock, and `app.notification.retention-days` (30) purges old SENT rows. `app.schedulers.enabled` (default true; false in the Gradle `test` task) guards the `@Scheduled` jobs. The offline gateway defaults to simulated; production must select SMTP (WARN otherwise), see [delivery configuration](../deployment/notifications.md).
- **Admin SSE**: registration/removal run inside `compute`; at the per-admin limit the *oldest* stream is evicted (reload/reconnect works) instead of 429; broadcasts and heartbeats go through a bounded executor (dropped + logged when saturated); heartbeats close streams whose JWT has expired, and a logout (token revocation, on any replica with `app.state.store=redis`) closes that token's streams. Appointment events are per replica, and role removal is not observed.
- **Catalog**: service names are unique case-insensitively (409 on clash); `DELETE` retires (`active=false`) a service that has bookings and hard-deletes one that has none; the public list, `GET /{id}` and booking see only active services. Admins list the retired ones with `GET /catalog/retired` and bring one back with `POST /catalog/{id}/restore` (idempotent; the unique name cannot clash because it is unique across active and retired rows). `/catalog/retired` sits under the public `GET /catalog/**` rule, so `SecurityConfig` names it first and the mobile `publicEndpoints.ts` allowlist excludes it (a public call there would go out without the token and answer 401). Hibernate L2/query caches are explicitly off (`l2-*` regions exist only for the benchmark).
- **No customer data in logs/traces**: notification delivery logs only the outbox id and failure class, never recipients/content or SMTP exception text; the `appointment.customer` span attribute was removed. The simulated gateway's `fail*`/`invalid*` recipient failure hook is off unless `app.notification.simulate-failures=true` and never applies to SMTP.
