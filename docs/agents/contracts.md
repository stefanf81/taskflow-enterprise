# Cross-platform contracts and the web ↔ mobile sync workflow

OpenAPI baseline, generated DTO types, shared tokens and the steps for porting a feature between platforms.

_Detail moved out of [`AGENTS.md`](../../AGENTS.md); the text is unchanged._

- **Platform-local contracts**:
  - `api/openapi.json`: reviewed, canonical OpenAPI contract baseline.
  - `shared/schemas/src/generated/api-types.ts`: the API DTO types, generated once from the baseline; `frontend/src/app/types/api.ts` and `mobile/src/types/api.ts` only re-export them (`export type *`), so the apps keep one import point and there is one generated copy. Response DTOs (every field typed as present, because the validators fill in omitted ones) are the schemas reachable from a 2xx response; the generator keeps no list of them.
  - The baseline also documents errors and security: every 4xx/5xx body is `ErrorResponse` (`core/web/OpenApiErrorResponseConfig`), except the 401/403 of an authenticated operation, which the filter chain answers without a body; `cookieAuth` (the HttpOnly `access_token` cookie) and `bearerAuth` (mobile) are alternatives, and public operations carry `security: []` from `auth/OpenApiSecurityConfig.PUBLIC_OPERATIONS`, which `OpenApiSecurityDocumentationTest` calls anonymously against the real filter chain. Content types are `application/json` (`springdoc.default-produces-media-type`).
  - `shared/schemas/src/generated/api-responses.ts`: structural zod/mini contracts for every response DTO, generated by the same script. They are not the runtime validators (those stay hand-written in `shared/schemas/src/*.ts` because they add enums, lengths and the "omitted means empty" defaults, which OpenAPI cannot express); `frontend/src/app/shared-schemas-contract.spec.ts` fails when a validator's field set, or whether a field may be absent, differs from the generated contract. Why it exists: zod objects drop keys they do not list, so a response field the backend adds would be stripped silently. Which fields may be absent comes from the spec: Jackson omits null fields globally, and `core/OpenApiResponseNullabilityConfig` marks every component of a response record `required` unless its type is JSpecify `@Nullable`, so **a response field that can be null must be annotated `@Nullable`**. The generator fails on a response schema without a `required` list. Adding a response DTO means adding it to `RESPONSE_SCHEMAS` there and to the contract→validator table in the spec.
  - `frontend/src/theme/tokens.json` and `mobile/src/theme/tokens.json`: Obsidian & Gold design system tokens.
  - `shared/domain/` (`@taskflow/domain`): the booking rules and time helpers both clients apply — opening days and the booking window (`ShopRules`, `isOpenOn`, `isWithinBookingWindow`, `openingHoursRows`), `isCustomerCancellable` (PENDING/APPROVED and not started, as the server decides), `NO_PREFERENCE_BARBER`, `normalizePublicId`, `shopWallClock` and the `HH:mm` helpers. Plain TypeScript without dependencies, with its own vitest suite (`npm run test:domain`) and strict `typecheck`. Never hard-code the shop's values: `GET /api/v1/appointments/public/shop` reports the time zone, `maxAdvanceDays` and the `openingHours` derived from the barbers' schedules; the web reads them through `core/shop-clock.ts` (`ShopClock.rules()`), mobile through `core/shop/useShopInfo.ts`, and both fall back to `DEFAULT_SHOP_RULES` (the server's built-in defaults) until it answers.
  - `frontend/src/app/core/time-utils.ts` and `mobile/src/utils/time-utils.ts`: each app's one import point for time helpers — the shared ones re-exported from `@taskflow/domain`, plus platform formatting (web) and the wizard's slot-selection helpers (mobile).
  - `frontend/src/component-map.json` and `mobile/src/component-map.json`: Cross-platform feature component mapping metadata.
## Cross-Platform AI Feature Synchronization Workflow

When modifying or porting a feature between Web (`frontend/`) and Mobile (`mobile/`):
1. **Lookup Component Mapping**: Inspect `frontend/src/component-map.json` or `mobile/src/component-map.json` to identify target files on both platforms.
2. **Use Opencode Sync Skill**: Reference `.opencode/skills/sync-to-mobile.md` for exact framework translation rules:
   * **State**: Angular Signals (`signal()`, `computed()`) $\rightarrow$ TanStack Query (`useQuery`) / Zustand (`useAuthStore`).
   * **Templates**: Angular `@if`/`@for` $\rightarrow$ React Native JSX conditionals & `FlatList`/`map()`.
   * **Theme**: Ensure color tokens originate from the platform-local token files (`mobile/src/theme/colors.ts`).
3. **Sync API Contracts**: If backend endpoints/DTOs change, start the backend, run `npm run api:spec:update`, then `npm run sync:api-types`. Commit the baseline and both generated client type files. Run `npm run sync:api-types:check` before finishing.
4. **Verify**: Run `npm run lint:all` and `npm run test:all`.
