# Containers, JVM runtime profiles and Nginx

One Dockerfile with two targets, JVM sizing ownership, container hardening, health checks, AOT cache and compose datastores.

_Detail moved out of [`AGENTS.md`](../../AGENTS.md); the text is unchanged._

  - Runtime Profiles & Multi-Arch JVM Optimization:
    - **One Dockerfile, two targets.** `Dockerfile` has shared `extractor`, `java-base`, `cds-training` and `runtime` stages and two final targets: `prod` (CI, `--target prod`, `platforms: linux/amd64`; per-build Ubuntu package refresh, `curl`/`wget`/`gnupg` purged, setuid bits stripped, no HEALTHCHECK) and `local` (compose `target: local`; `wget` + HEALTHCHECK, no apt layer of its own; the last stage, so also the default target of an untargeted build). tini and `wget` are installed once, in `runtime`, before the application layers, so a new JAR never re-runs apt; neither is version-pinned, so an uncached build can resolve newer ones. `wget` must be installed there: the Java 25 base ships no curl/wget/gnupg, and without it every compose health check fails (§62). Both `apt-get update` calls use `--error-on=any` (by default APT only warns on a failed download, and the prod upgrade would then succeed without those updates; `ContainerImageBenchmarkTest` guards it). `runtime` replaces the base's inherited Ubuntu `title`/`description` OCI labels; the account home is `/nonexistent`. Build `prod` by hand with `docker build --platform linux/amd64 --target prod .`. The target architecture is chosen by the builder, never hardcoded in the file: compose builds for the host, the workflows pass `linux/amd64`; only the extractor stage pins `$BUILDPLATFORM`.
    - **JVM sizing is deployment-owned.** The image CMD (shared `runtime` stage) is sizing-agnostic: it carries only environment-invariant flags (`-XX:AOTCache=application.aot`, `-XX:+ExitOnOutOfMemoryError`). Heap / off-heap / GC behavioral tuning live in `JAVA_TOOL_OPTIONS` of the runtime environment, NOT the image. Setting sizing in the CMD would silently win over the deployment env (JVM last-wins precedence for non-sticky flags) and recreate the precedence bug where the deployment's tuning was a no-op.
    - **Local (Apple Silicon M4 Pro):** the `local` target, built natively for the host architecture, ships only runtime invariants. Heap / off-heap sizing and behavioral GC flags are set via `JAVA_TOOL_OPTIONS` in `docker-compose.yml` (50% × 2560M limit ≈ 1.25 GiB heap, G1GC + AlwaysPreTouch + MaxDirectMemorySize=256m + MaxMetaspaceSize=256m).
    - **Production (AMD Ryzen 5 7430U):** the `prod` target, built by the workflows for `linux/amd64`. The image is sizing-agnostic; JVM sizing is owned by `homelab/TF/gitops/apps/taskflow/backend.yaml` `JAVA_TOOL_OPTIONS`: `MaxRAMPercentage=50.0` (50% × 2Gi = 1 GiB heap, leaving 1 GiB for off-heap), `MaxDirectMemorySize=256m`, `MaxMetaspaceSize=256m`, plus behavioral GC flags (G1GC, `MaxGCPauseMillis=100`, AlwaysPreTouch) and heap-dump-on-OOM. CPU-pinned GC/AVX flags are deliberately omitted so the JVM reads the container's actual CPU allocation.
    - **Healthcheck Divergence (P1-6 §47):** The `local` target carries `HEALTHCHECK --interval=30s --timeout=5s --retries=3 --start-period=60s --start-interval=2s CMD wget -qO /dev/null http://localhost:8080/actuator/health/liveness` for standalone `docker run` & `depends_on: condition: service_healthy`. The `prod` target intentionally omits `HEALTHCHECK` — K8s `livenessProbe`/`readinessProbe` in `homelab/TF/gitops/apps/taskflow/backend.yaml` is the source of truth.
    - **Production manifests live in a separate repo** (`homelab/TF/gitops/apps/taskflow/`), not in this workspace.
- **Container Hardening & Zero-Trust**:
  - **Numeric UIDs**: Backend containers are configured with a hardcoded, unprivileged numeric UID (`10001:10001`) to comply with strict Kubernetes Pod Security Standards (PSS).
  - **Zero-Trust Networks**: `docker-compose.yml` isolates the DB and Cache on the `backend-tier` network. The Nginx reverse proxy is on the `frontend-tier`. The backend bridges both. The frontend cannot physically talk to the database.
  - **Read-Only Root**: Application containers (`backend`, `frontend`) mount read-only filesystems with ephemeral directories mounted as `tmpfs` (e.g., `/tmp`, `/var/cache/nginx`), preventing runtime binary tampering.
  - **Dropped Capabilities**: Edge application containers completely drop kernel privileges (`cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`); datastores (`db`, `redis`, `jaeger`) use standard container defaults.
  - **Container Lifecycle**: `docker-compose.yml` uses `restart: "no"` so containers do not linger across system/Docker reboots. Verification and E2E scripts (`./verify.sh`, `npm run e2e:docker`) use exit traps (`./stop-docker.sh`) to automatically stop containers after test completion.
  - **Graceful Shutdown**: Spring drains for 30 seconds (`server.shutdown=graceful`, `spring.lifecycle.timeout-per-shutdown-phase=30s`) and the Compose backend has a 40-second `stop_grace_period`. Keep production `terminationGracePeriodSeconds` longer than the Spring shutdown phase in the separate GitOps repository.
- **Healthcheck Divergence (P1-6 §47)**: The Dockerfile's `local` target `HEALTHCHECK --interval=30s --timeout=5s --retries=3 --start-period=60s --start-interval=2s CMD wget -qO /dev/null http://localhost:8080/actuator/health/liveness` for `docker run` parity & `depends_on: service_healthy`; the `prod` target intentionally omits `HEALTHCHECK` — K8s `livenessProbe`/`readinessProbe` in `homelab/TF/gitops/apps/taskflow/backend.yaml` owns prod.
- **UseContainerSupport & Diagnostics (P1-2 §43)**: Explicit `-XX:+UseContainerSupport` (self-documenting cgroup-aware), `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/taskflow` (0% until OOM) + `-Xlog:gc*:file=/var/log/taskflow/gc.log:time,uptime:filecount=3,filesize=10m` (~0.7% overhead) in `JAVA_TOOL_OPTIONS` (`docker-compose.yml` local 1.25 GiB heap, `homelab/TF/.../backend.yaml` prod 1 GiB). They go to `/var/log/taskflow`, which the image's `runtime` stage creates owned by 10001 and compose mounts as the `backend-diagnostics` named volume — not the `/tmp` tmpfs, whose pages count against the memory limit and vanish when `ExitOnOutOfMemoryError` stops the container. The dump is `java_pid<pid>.hprof` and is never overwritten; under tini the JVM gets the same PID on every start, so until that file is deleted every later OOM writes no dump (`Unable to create … File exists`) — delete it after analysis; the GC log rotates the previous run to `gc.log.0`.
- **glibc Tuning on Ubuntu Base (§51)**: backend base is `eclipse-temurin:25-jre-resolute` (Ubuntu 26.04 LTS, digest-pinned, Java 25 since §62; Alpine→glibc re-baseline: throughput/latency parity, +59 MiB RSS, +40 MB image, 0 vs 6 fixable HIGH/CRITICAL on the local variants). Adopted `MALLOC_ARENA_MAX=2` in `docker-compose.yml` backend env (glibc-only knob: arenas default to 8×cores and throttle RSS; measured −72 MiB median with no throughput/GC cost; mirror in `homelab/TF`). Rejected: jemalloc preload (+165 MiB RSS, `libjemalloc2` deliberately not shipped) and `-XX:+UseTransparentHugePages` (local VM THP=`always` already collapses pages). Harness `scripts/benchmark-glibc-tuning.sh` (fails if 0 2xx — the public rate-limit bucket 429s a raw `hey` sweep); assertions in `GlibcTuningBenchmarkTest`.
- **AOT Cache Training & Slim Prod Image (§56/§62)**: the Dockerfile's shared `cds-training` stage trains the Java 25 **AOT cache** (`-XX:+UseG1GC -XX:AOTCacheOutput=/tmp/application.aot`, JEP 483/514/515; it replaced the dynamic CDS archive in §62) on the full app (default profile, in-memory H2, `RUN --network=none`, `env -i` drops BuildKit's injected `OTEL_*`, `spring.context.exit=onRefresh`); the `CMD` loads it with `-XX:AOTCache=application.aot` (default `AOTMode=auto`). Prod-profile startup medians: Java 21 + CDS 3.19 s → Java 25 + AOT cache 2.67 s (−16%; Java 25 with the old CDS archive 3.23 s); harness `scripts/benchmark-cds-startup.sh`. Both targets verify the cache by **booting the app** with `-XX:AOTMode=on` (same flags as the training run), not `java -version`: `-version` maps only JDK classes and passed with an archive that crashed the real startup (fat-JAR archive, Ubuntu OpenJDK 21.0.12). Compact object headers were measured and not adopted: they change the object layout, so the cache would have to be trained with the flag and the image `CMD` would have to carry it (a `JAVA_TOOL_OPTIONS`-only setting silently drops the cache). §62 observed no clear throughput regression on two cached endpoints on arm64, with up to 18.1% within-image spread; it did not establish equivalence. Accumulated pause time on `/barbers` increased ~30%. Native amd64 validation is a pre-production gate because §58 measured −5–8% there. Spring Modulith is test-only (`spring-modulith-starter-test` for `ModularityTest`; the runtime starter added unused Moments `@hourly`/`@daily` jobs, ArchUnit and the annotation processor, §61); `hibernate-jcache`/`caffeine-jcache` are `testImplementation` (L2 is off; only the L2 benchmark/settings tests use them) — the boot JAR shrank 95.6 → 89.1 MB. The `prod` target purges `curl`/`wget`/`gnupg` (+30 deps), removes the base's unmanaged Pebble Go binary (`/usr/bin/pebble` + `/var/lib/pebble` — apt cannot patch its Go stdlib; 3 HIGH Trivy findings on 2026-10-10), and strips setuid/setgid bits; the `local` target keeps `wget` (installed in `runtime`, the Java 25 base has none) for `HEALTHCHECK`. Assertions in `ContainerImageBenchmarkTest` and `ContainerConfigGuardTest` (one Dockerfile, two targets, builder-owned platform, tini before the layers, `local` as default), run by `./gradlew containerConfigTest` (tag `container-config`, excluded from `test`).
- **Nginx** frontend container runs on unprivileged port 8080 (mapped from host 4200). `nginx-main.conf` has `open_file_cache` (the assets are a read-only image layer), a buffered access log (`buffer=4k flush=1s`: 4 KiB = PIPE_BUF keeps the shared stdout pipe line-atomic; lines can lag 1 s) and `worker_rlimit_nofile 8192` (Docker 29/containerd 2.1.5 start containers at a 1024 soft limit); together `/` 46k → 80k rps at `cpus: 1.0` (§59). No `proxy_cache` microcache: it would hide the JVM from k6/the glibc harness and bypass the rate limiter.
- **Compose datastores (§59)**: `db` has `shm_size: 256mb` (parallel hash joins failed at Docker's 64 MB `/dev/shm`) and a TCP `pg_isready -h 127.0.0.1` probe (the init server listens on the socket only); Redis runs without `--io-threads` (1 CPU: threads raised p50 latency and cut throughput up to 45%). PostgreSQL uses `wal_compression=lz4` (cheapest of pglz/lz4/zstd at ~70% less WAL). Jaeger keeps `max_traces: 20000` with `GOMEMLIMIT=200MiB` inside its 256M limit; Jaeger 2.22 enables MCP with an `ai: mcp: {}` block (the old `enable_mcp` key fails validation and Jaeger exits). Every health check has `start_period` + `start_interval`, so `depends_on: service_healthy` follows the real boot time.
