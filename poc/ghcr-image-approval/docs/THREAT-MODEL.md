# Threat model, guarantees and outstanding production blockers

## What this reference can detect

The base-image comparator does not execute images. It detects changes in OCI config, packages/SBOM, known CVEs, executable and interpreted files, directory permissions/ownership, symlinks and hardlinks, and produces human-readable diffoci output. The custom policy requires review for unexpected changes and blocks unacceptable vulnerabilities; it is **not** a malware detector. A backdoor replacing an expected JDK file may look like an ordinary update.

An internal image signature proves the organization's approval identity signed a digest. It is not evidence that the image is benign, nor is a digest proof of publisher authenticity. The workflow intentionally marks upstream provenance `not_verified` until supplier-specific source/builder attestations are independently verified. It will normally require a human for third-party updates.

The app workflow uses independent source builds and independent deterministic image builds. Signed GitHub artifact attestations bind each builder's output files (TAR, image config digest, base-image lists) to the expected central workflow and protected branch. The scan job (read-only) checks both builders agree; the separate push job pushes the attested TAR; the promotion job checks both independent attested config digests against the GHCR candidate manifest's `config.digest`. The config embeds rootfs diff IDs, binding uncompressed layers. This **narrows** a compromised scanner's substitution options considerably compared with accepting only its PASS JSON, but cannot protect against both builders being compromised or a compromised protected workflow.

The independent rescan and verifier run after promotion. The verifier's key never needs to parse the image. The final application signer verifies its signed evidence, checks the exact application digest, and fetches a fresh signed release authorization.

## What has not been proven

- **Live infrastructure:** No release workflow was run against GitHub Actions, private GHCR, the release-gate API or an EKS staging cluster.
- **Release gate:** A separately operated, cryptographically authenticated grant service is required but not implemented here. It must validate protected refs, required checks, revocation and authorization, and issue a fresh grant on request. A GitHub environment manual review alone is insufficient to prove the source checks passed.
- **Independent SLSA level:** GitHub artifact attestations establish identity of the central workflow and subject files. They do not automatically prove that an arbitrary external application commit was built from the expected source files, and the locally constructed build record is **not** independently generated SLSA Build Level 3 provenance. Consider trusted reusable workflows and separately asserted materials/source for stronger assurance.
- **Runner hardening:** Hosted runners provide fresh machines. All actions are pinned to full commit SHAs, the Docker engine version is pinned for the image builders, and crane, cosign, Syft, Grype, diffoci and gh are installed from size- and SHA-256-pinned release files; `require_tools.sh` refuses unpinned copies of them. Not covered: the remaining runner-image tools (python3, jq, git, curl, openssl), scanner DB integrity/freshness, runner network policy and GitHub organization policies. The tool hashes were compared with the publishers' checksum files, not with independently verified signatures. Review pin updates like code.
- **GHCR consistency:** The approval tracking tag read/check/write is NOT a registry compare-and-swap transaction. A single writer beyond GitHub workflow concurrency and GHCR package Actions access must be configured and verified; GITHUB_TOKEN write is not scoped to one package within the same trusted repository.
- **Private artifact attestations:** Support varies by GitHub plan. For unsupported plans, this implementation **fails closed** rather than silently skipping verification.
- **Full platform coverage:** The public Temurin index is evaluated for all runnable platforms. Application image builders currently target one Linux platform; configure separate attestations/promotion and admission checks before adding an ARM64 release matrix.
- **CVE exception provenance:** The original v10 base-image exception inheritance trusted package discovery locations even when application layers could have modified the package's files; v2 therefore rejected all inherited base exceptions. v3 inherits a `base_image_ref` exception only with two proofs: Grype located the package in a base layer, and the application layers are purely additive (no base path overwritten, deleted by a whiteout, hidden by an opaque whiteout or written through a symlink), checked from the layer bytes whose digests are bound to the image config. Residual risk: an additive layer can still change behaviour without touching base files (for example `LD_PRELOAD` in the image config or a new file earlier on a search path); the exception is about the vulnerable package's bytes, not about the image as a whole. Layer compression other than gzip/none (e.g. zstd) is reported as not additive.
- **Approval fingerprint:** A signed base approval records a fingerprint of the base-evaluation code, settings and tool pins. It only decides whether the precheck may skip an already approved digest. Historical versions may be read solely to compare against the previous baseline during evaluation/promotion; application builds require the current accepted version and current policy fingerprint. An image signed under older policy code is not automatically permitted for new builds.
- **Signature format:** cosign v3 writes its new bundle format. Verification with the same cosign works; Kyverno's support for that format on GHCR is untested here.
- **Kyverno policy:** The included YAML is a starting point for v1.20+ and uses placeholders and no live CEL/admission tests; it must be adapted to the actual Kyverno and GHCR deployment before any Deny rollout.
- **GitHub Actions limitations:** Workflow artifact attestations are specific to the GitHub-hosted identity and repository. Protect the central default branch and CODEOWNERS; a compromised central workflow or signing environment can abuse its legitimate identity.
- **Retention and incident response:** The example uploads evidence with finite retention but does not configure WORM storage, historical provenance retention, revocation automation, emergency key rotation, scheduled rescans or SLSA transparency-log operations. Adopt separate control-plane services for these functions.
- **Supply-chain trust:** A compromised legitimate upstream publisher may distribute a malicious image with valid signatures and well-formed provenance. Independent builds, controlled runtime privileges/network access and runtime monitoring remain important.

## Blocking staging tests (before production signing authority)

1. Prove the required GitHub Actions environments cannot be bypassed from a PR, tag or alternate branch, and the reviewer identity is accurately obtained.
2. Exercise release-gate revocation during a long-running release. Signing must fail closed.
3. Prove incorrect/TAR-substituted builder artifacts fail GitHub attestation verification.
4. Prove the GHCR candidate is rejected when its config digest differs from either independently GitHub-attested builder config digest, and that the push job refuses an archive or digest different from the one the scan approved.
5. Validate archive decompression and size limits on application outputs; container image decompression limits also require infrastructure policy.
6. Validate Grype/Syft/Crane/diffoci/Cosign invocation syntax on pinned actual tool versions, including database refresh and local registry authentication.
7. Validate manual High-CVE approval references the exact signed scan findings and cannot approve an unrelated digest; the protected verifier must reject new findings.
8. Validate Cosign attestation predicate shape and every Kyverno rule in a staging EKS cluster, including init/ephemeral containers and mixed sidecars.
9. Validate promotion rollback/revocation, secret access, registry network isolation and protection against concurrent out-of-band GHCR writers (GHCR does not provide Harbor-style package namespace isolation).
10. Schedule rescan/reassessment of approved and deployed digests, plus patch SLA and time-limited exception handling.

**Decision rule:** treat this archive as a design and test harness until these controls have passed in your environment, not as an organization-wide 'approved/secure image' guarantee.

## GHCR-specific authorization limitation

The workflow uses per-job `GITHUB_TOKEN` with `packages: read/write`. This is less granular than separate Harbor project robot accounts. A repository granted write access to multiple GHCR packages may publish to all of them when a job requests `packages: write`; environment approvals are not package-specific ACLs. v3 keeps write tokens out of every job that parses image content (base evaluate and application scan are read-only; the quarantine copy and candidate push are separate small jobs), so a parser exploit no longer yields a write token.

Workflow YAML cannot protect against a repository writer who pushes a branch or tag with a **modified** workflow and dispatches it: that run can request `packages: write` without any environment. Only repository settings stop this - rulesets restricting branch and tag creation, read-only default workflow permissions, environments limited to `main`. `ci/audit_repo_settings.py` checks those settings; run it after every settings change. Keep unsigned candidates separate from signed and policy-attested approval, require key-based verification in Kyverno, and consider separate CI repositories/identities for the strongest isolation.

No current live GitHub Actions/GHCR/Kyverno integration test proves signature persistence, multi-platform digest preservation, private-package access, or admission-policy CEL evaluation. These must be validated in staging. GHCR tracking tags are mutable in this example; digest-only consumers and protected writers are mandatory.
